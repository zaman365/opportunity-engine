# ADR-017 · MF-ASSET-01 needs a browser, and its own fixtures

**2026-09-21 · accepted**

## Problem

`contracts/detectors.json` sets MF-ASSET-01's bar at "Resource failure plus actual
rendered-image failure after bounded lazy-load wait", abstaining on `blocked`,
`pending_lazy_load`, `decorative_image` and `variant_changed`. BUILD_SPEC.md adds:
"HTTP/resource and rendered-image evidence; **not just lazy-load timing**."

MF-LINK-01 needed only an HTTP status. This rule needs two facts the M1 capture path did not
produce: what each image request returned, and whether the browser actually painted it.

## Decision

**Both halves, or the rule abstains.** A failed request alone could still paint from cache; a
blank render alone could be styling, an unsupported format or a decode failure. A candidate
requires a rendered failure _and_ resource evidence that explains it — an error status, an
empty 2xx body, or no response at all — agreeing across two independent comparable sessions.
A 200 that returned a real body and still did not paint produces
`rendered_without_resource_evidence`, which goes to a reviewer rather than becoming a claim.

**Images are subresources of a page, not extra pages.** They never change
`expected_unique_pages` / `captured_unique_pages`. The scan reports how many images it checked
and how many were classified as product content, separately.

**Each image is its own evidence row.** `capture_role = 'product_image'`, its own URL, status,
hash and bytes when the response carried a usable image. Folding them into the page evidence's
JSON would make them unciteable, and a finding has to point at the exact observation it rests
on.

**Classification is deliberately asymmetric.** `product` requires a positive signal —
non-empty `alt`, not marked presentational, inside the content area. Empty `alt` or
`role="presentation"` is `decorative`. Everything else is `unknown`, and the rule abstains on
anything that is not `product`. A broken image with no alt text is therefore missed rather
than asserted. That is the right trade: the alternative is telling a merchant their product
photography is broken because a spacer image 404'd.

**The bounded wait is a real timeout, not a sleep.** Each image request gets
`limits.imageTimeoutMs` (2s). A request still outstanding when it expires is recorded as
`timedOut`, and the rule returns `pending_lazy_load`. A slow image is never described as a
broken one.

**The render is offline and fulfilled from recorded bytes.** Every request the page makes is
intercepted: the document from the HTML the transport recorded, each image from the bytes the
transport already fetched, everything else aborted. With JavaScript disabled, nothing in the
page can initiate a request the handler has not seen. So the painted result is a picture of
the responses we observed, never a second live retrieval.

## A bug this design caused, and the fix

The renderer originally injected markup with `setContent`, which leaves the document at
`about:blank`. Root-relative image paths then resolve to nothing, every image fails to render,
and a healthy page becomes a false positive. The renderer now navigates to the page's real URL
with the response fulfilled from the recorded HTML, so relative paths resolve the way they did
during capture. Nothing reaches the network either way.

## Fixtures

`fixtures/m2-server.mjs`, loopback only, GET and HEAD only, on its own port. The kit's fixture
server is untouched; its README says additional lazy-load and variant fixtures belong in M2.

One route per branch of the rule: `product-broken-image` (known positive, 404),
`product-empty-image` (200 with no body), `product-healthy` (negative control),
`product-lazy` (delayed past the bounded wait), `product-decorative-broken` (only a
presentational image fails), `product-variant` (different product state per request).

Images are generated by a small PNG encoder rather than committed as binaries, so a reviewer
can see from source exactly what each route serves — including a deliberately empty response,
which would be an unreadable corrupt file on disk.

## Alternatives rejected

- **Resource status alone.** Cheaper and browserless, but it calls a cached image broken and
  misses an image that arrives and fails to decode. It is also precisely what the detector
  spec says not to do.
- **Render alone.** Produces a claim with nothing to repair: "it did not appear" with no
  explanation is not actionable.
- **Treating a timeout as a failure.** Would make the rule's verdict depend on network weather.
- **Relaxing the capture policy for subresources.** Every image URL passes the same target
  policy as the page. An image on an unapproved host is never requested.

## Contracts

`CreateScan.detectors` accepts `MF-ASSET-01` and up to two entries; `Evidence` gains
`observation`. Both are in `contracts/overlay.json` with their reasons, and
`generated-contract.test.ts` proves the request-side change only widens. Migration 0008 adds
the `product_image` capture role and widens the scan's detector allowlist.

## Verification

`tests/unit/detector-asset.test.ts`: every declared abstention has a case, plus the three
failure kinds, the negative control, classification and parsing. 33 assertions.

`tests/integration/asset-detector.test.ts`: all six fixture routes end to end through the real
API, database, image requests and Chromium render, plus review, report, root-cause grouping
and the subresource host policy.

`tests/e2e/operator.spec.ts`: the grid renders one row per inspected item; a 200 that never
painted reads as a failure cell; the decorative and pending cases never use defect language.
